# 📘 Часть 13: TypeScript с React (кратко)

> **О структуре:** минимально необходимый TypeScript для React-разработчика: типизация пропсов, хуков, событий и API. Каждая тема — с **сравнением JS ↔ TS**, чтобы видеть, что именно добавляет TypeScript и зачем.

---

## 13.1 Зачем TypeScript в React

TypeScript добавляет **статические типы** в JavaScript. Ошибки ловятся **до** запуска кода — в редакторе.

**Что ты получаешь:**
- Автодополнение пропсов и полей объектов
- Ошибка при передаче неверного пропса — сразу, а не в рантайме
- Безопасный рефакторинг: переименовал поле — TS покажет все места, где надо обновить
- Самодокументируемый код: типы описывают контракт компонента

**Что НЕ нужно изучать за один день:** классы, декораторы, сложные дженерики, mapped types. Для React-разработчика 90% задач покрываются тем, что ниже.

### Сравнение: одна и та же ошибка в JS и TS

**JS-версия:**
```jsx
function UserCard({ user }) {
  return <p>{user.nmae}</p>; // опечатка: nmae вместо name
}
```
Приложение **упадёт в рантайме** с `Cannot read property 'nmae' of undefined` — или, что хуже, отрендерит `undefined` молча, и ты будешь искать баг глазами.

**TS-версия:**
```tsx
interface User { name: string }

function UserCard({ user }: { user: User }) {
  return <p>{user.nmae}</p>;
  //            ~~~~~ Property 'nmae' does not exist on type 'User'.
}
```
Ошибка видна **в редакторе сразу**, ещё до запуска. Красное подчёркивание + подсказка с правильным полем.

## 13.2 Настройка проекта с TypeScript

```bash
npm create vite@latest my-app -- --template react-ts
```

Vite создаст `tsconfig.json`, `tsconfig.app.json`, `tsconfig.node.json` и файлы `.tsx` вместо `.jsx`.

**Правило:** любой файл с JSX должен иметь расширение `.tsx`.

### Сравнение структуры

| JS-проект | TS-проект |
|-----------|-----------|
| `App.jsx` | `App.tsx` |
| `main.jsx` | `main.tsx` |
| `api/posts.js` | `api/posts.ts` |
| `components/Button.jsx` | `components/Button.tsx` |
| — | `tsconfig.json` |

Сам код почти не меняется — только добавляются типы и расширения файлов.

## 13.3 Типизация пропсов

### Простой интерфейс

**JS:**
```jsx
function Button({ label, onClick, disabled }) {
  return <button onClick={onClick} disabled={disabled}>{label}</button>;
}

// Использование
<Button label="OK" onClick={() => {}} />
<Button label={42} />           {/* не падает — просто отрендерит "42" */}
<Button />                       {/* не падает — label=undefined */}
```

**TS:**
```tsx
interface ButtonProps {
  label: string;
  onClick: () => void;
  disabled?: boolean; // ? — опциональный
}

function Button({ label, onClick, disabled = false }: ButtonProps) {
  return <button onClick={onClick} disabled={disabled}>{label}</button>;
}

// Использование
<Button label="OK" onClick={() => {}} />
<Button label={42} />           // ❌ Type 'number' is not assignable to type 'string'
<Button />                       // ❌ Property 'label' is missing
```

**Что изменилось:**
- JS: пропущенный или неверный пропс — тишина до рантайма
- TS: ошибка в редакторе
- `disabled?: boolean` — говорит «пропс необязательный»
- `disabled = false` — значение по умолчанию (как в JS), но теперь ещё и тип гарантирует, что придут только `boolean`

**Правило:** для пропсов используй `interface`, а не `type` — интерфейсы расширяются через `extends` и дают лучшие сообщения об ошибках.

### `children` — `React.ReactNode`

**JS:**
```jsx
function Card({ title, children }) {
  return <div><h3>{title}</h3>{children}</div>;
}
// children может быть чем угодно — и это нормально
```

**TS:**
```tsx
interface CardProps {
  title: string;
  children: React.ReactNode;
}

function Card({ title, children }: CardProps) {
  return <div><h3>{title}</h3>{children}</div>;
}
```

`ReactNode` — самый широкий тип: строка, число, JSX, массив, `null`. Используй его для `children`.

**Альтернативы:**
- `React.ReactNode` — «что угодно, что React умеет рендерить» (в 99% случаев)
- `React.ReactElement` — только **один** JSX-элемент (не строка, не массив)
- `JSX.Element` — конкретный JSX-элемент (устаревает, лучше `ReactElement`)

### Расширение HTML-атрибутов

Когда компонент — обёртка над нативной кнопкой.

**JS:**
```jsx
function IconButton({ icon, children, ...rest }) {
  return (
    <button {...rest}>
      {icon} {children}
    </button>
  );
}
// Пробросит любой атрибут: onClick, disabled, type, className... 
// но редактор не подскажет, какие есть
```

**TS:**
```tsx
interface IconButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  icon: React.ReactNode;
}

function IconButton({ icon, children, ...rest }: IconButtonProps) {
  return (
    <button {...rest}>
      {icon} {children}
    </button>
  );
}

// Использование — автодополнение ВСЕХ кнопочных атрибутов
<IconButton icon="🔍" onClick={handleSearch} type="submit" disabled />
```

**Что изменилось:**
- `extends React.ButtonHTMLAttributes<HTMLButtonElement>` — говорит «у меня есть все атрибуты кнопки»
- Редактор подсказывает `onClick`, `type`, `disabled`, `aria-label` и т.д.
- Опечатка (`onClik`) — сразу ошибка

## 13.4 Типизация хуков

### `useState`

**JS:**
```jsx
const [count, setCount] = useState(0);           // может быть чем угодно
const [user, setUser] = useState(null);           // "null" — не тип, а значение
const [status, setStatus] = useState('idle');     // "idle" — не тип
```

**TS:**
```tsx
const [count, setCount] = useState(0);            // TS выведет: number
const [name, setName] = useState('');             // string
const [isOpen, setIsOpen] = useState(false);      // boolean

// Если начальное значение — неполное (null), указываем тип явно:
interface User { id: number; name: string }
const [user, setUser] = useState<User | null>(null);

// Для union-типов (статусы):
type Status = 'idle' | 'loading' | 'success' | 'error';
const [status, setStatus] = useState<Status>('idle');
```

**Что изменилось:**
- В простых случаях (`0`, `''`, `false`) TS **выводит** тип сам — ничего писать не надо
- Если начальное значение `null` — нужен явный generic `useState<T | null>(null)`, иначе TS выведет «только null» и присвоить `User` не даст
- Для union-типов (`Status`) — автодополнение только четырёх строк и ошибка при опечатке:

```tsx
setStatus('loading'); // ✅
setStatus('loding');  // ❌ Type '"loding"' is not assignable to type 'Status'
```

В JS `setStatus('loding')` пройдёт молча, а потом `switch` в рендере не найдёт case — и ты будешь искать баг в другом месте.

### `useReducer`

**JS:**
```jsx
function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    case 'set': return { count: action.value }; // откуда value? не проверяется
    default: return state; // легко забыть case — и молча ничего не произойдёт
  }
}
```

**TS — discriminated union:**
```tsx
interface State { count: number }

type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'set'; value: number };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    case 'set': return { count: action.value };
    // TS проверяет: все case покрыты. Если забыл case — ошибка
  }
}

const [state, dispatch] = useReducer(reducer, { count: 0 });

// Использование:
dispatch({ type: 'set', value: 10 });      // ✅
dispatch({ type: 'set' });                  // ❌ Property 'value' is missing
dispatch({ type: 'incremente' });           // ❌ Type '"incremente"' is not assignable
```

**Что изменилось:**
- В `case 'set'` TS знает, что у `action` есть `value: number`. В остальных — нет. Это **type narrowing**.
- Если забыл обработать какое-то действие — TS выдаст ошибку «not all code paths return a value».
- `dispatch` проверяет, что ты передаёшь корректный объект action.

### `useRef`

**JS:**
```jsx
const inputRef = useRef(null);
inputRef.current?.focus(); // ?. — потому что не знаешь, что там
inputRef.current.value;    // упадёт, если это div, а не input
```

**TS:**
```tsx
const inputRef = useRef<HTMLInputElement>(null);
inputRef.current?.focus(); // ✅ focus() существует
inputRef.current?.value;   // ✅ value существует

// Если привязать к <div> — ошибка:
// <div ref={inputRef} />  ❌ Type 'HTMLDivElement' is not assignable to 'HTMLInputElement'
```

**Что изменилось:**
- Generic `<HTMLInputElement>` говорит «это ref на input»
- Редактор подсказывает методы именно `HTMLInputElement`: `focus()`, `select()`, `value`, `checked`
- Привязка к неправильному тегу — ошибка сразу
- `?.` по-прежнему нужен: `current` равен `null` до монтирования

### `useContext`

**JS:**
```jsx
const AuthContext = createContext(null);

function useAuth() {
  const ctx = useContext(AuthContext);
  // Если забыл Provider — ctx === null, а ошибка вылезет позже
  return ctx;
}

// Использование
const { user } = useAuth(); // упадёт, если контекст null
```

**TS:**
```tsx
interface AuthContextValue {
  user: User | null;
  login: (email: string) => void;
}

const AuthContext = createContext<AuthContextValue | null>(null);

function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used within AuthProvider');
  return ctx; // TS знает: ctx — AuthContextValue (не null)
}

// Использование
const { user } = useAuth(); // ✅ TS уверен, что user существует
```

**Что изменилось:**
- Явный `AuthContextValue` — автодополнение полей `user`, `login`
- Проверка `if (!ctx) throw` — единственное место, где обрабатывается «нет провайдера»
- После проверки TS **сужает** тип до `AuthContextValue`, и все потребители получают его без лишних проверок

## 13.5 Типизация событий

**JS:**
```jsx
function handleChange(e) {
  setValue(e.target.value); // e — любой, редактор не подсказывает
}

function handleClick(e) {
  console.log(e.currentTarget); // что здесь? никто не знает
}
```

**TS:**
```tsx
function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setValue(e.target.value); // ✅ string
}

function handleClick(e: React.MouseEvent<HTMLButtonElement>) {
  console.log(e.currentTarget); // ✅ HTMLButtonElement
}

function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
}

function handleKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
  if (e.key === 'Enter') { /* ... */ }
}
```

**Что изменилось:**
- `e.target.value` — редактор знает, что это `string` (для `<input>`)
- `e.currentTarget` — конкретный `HTMLButtonElement`, с методами
- Опечатка в `e.preventDefault` — сразу ошибка

**Правило:** generic-параметр — это тип **элемента**, на котором висит обработчик:

| Элемент | Тип события |
|---------|-------------|
| `<input>` | `React.ChangeEvent<HTMLInputElement>` |
| `<textarea>` | `React.ChangeEvent<HTMLTextAreaElement>` |
| `<select>` | `React.ChangeEvent<HTMLSelectElement>` |
| `<button>` | `React.MouseEvent<HTMLButtonElement>` |
| `<form>` | `React.FormEvent<HTMLFormElement>` |

## 13.6 Типизация API и Zod

Самый мощный паттерн: **Zod-схема → тип → валидация**.

**JS (с Zod, но без TS):**
```js
const userSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  age: z.coerce.number().int().positive(),
});

// Тип не извлекается — приходится описывать отдельно вручную
// и следить, чтобы он не разошёлся со схемой
```

**TS:**
```tsx
import { z } from 'zod';

const userSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  age: z.coerce.number().int().positive(),
});

// Извлекаем TypeScript-тип из схемы
type UserInput = z.infer<typeof userSchema>;
// { name: string; email: string; age: number }
```

**Что изменилось:**
- Один источник правды: правила валидации и тип не расходятся
- Изменил схему — TypeScript сразу покажет все места, где сломалось
- Работает и на клиенте (валидация формы), и на сервере (если Node)

### `z.input` vs `z.output` — важный нюанс

Из-за `z.coerce` **входной** тип (то, что в инпуте) и **выходной** (после преобразования) различаются:

```tsx
type FormInput  = z.input<typeof userSchema>;   // { age: unknown } (строка из инпута)
type FormOutput = z.output<typeof userSchema>;  // { age: number } (после coerce)
```

`useForm` из React Hook Form типизируется **входным** типом (там `age` — строка), а `onSubmit` получает **выходной** (там `age` — число):

```tsx
const { handleSubmit } = useForm<FormInput, unknown, FormOutput>({
  resolver: zodResolver(userSchema),
});

// В onSubmit приходит уже преобразованный объект
const onSubmit = (data: FormOutput) => {
  console.log(data.age); // number ✅
};
```

В JS это неважно — там `age` может быть и строкой, и числом, и никто не заметит. В TS — это помогает не забыть про `coerce`.

## 13.7 Практика Части 13: перевод компонента на TypeScript

Возьми `PostForm` из Части 11 и добавь типы.

### Что сделать

1. **Переименуй** `src/schemas/postSchema.js` → `postSchema.ts`
2. **Добавь тип поста** — `export type Post = z.infer<typeof postSchema>;`
3. **Типизируй пропсы `PostForm`:**
```tsx
interface PostFormProps {
  initialData?: Post;
  onSubmit: (data: Post) => Promise<void>;
  isEdit?: boolean;
}
```
4. **Типизируй `useForm`:**
```tsx
const { register, handleSubmit, formState } = useForm<Post>({
  resolver: zodResolver(postSchema),
  defaultValues: initialData ?? defaultPostValues,
});
```
5. **Типизируй `useFieldArray`:**
```tsx
useFieldArray<Post, 'tags'>({ control, name: 'tags' });
```
6. **Проверь:**
   - Если передать в `PostForm` пропс с опечаткой (`initialDat` вместо `initialData`) — TS должен ругаться
   - Если передать `initialData` не того типа (например, `{ title: 42 }`) — ошибка
   - Если попытаться обратиться к `form.title.toUpperCase()` — работает, потому что TS знает `title: string`

### Сравнение результата

| Место | Без TS | С TS |
|-------|--------|------|
| Пропсы `PostForm` | Не проверяются | Ошибка при опечатке |
| `useForm` | Любой `onSubmit` | `data: Post` — автодополнение полей |
| `register('title')` | Просто строка | Автодополнение полей `Post` |
| `errors.title` | Может быть чем угодно | `FieldError \| undefined` |
| `useFieldArray` | Не знает структуру | Знает, что `tags` — массив строк |
